Host Header Injection

İstemcinin gönderdiği Host başlığının doğrulanmadan güvenilir kabul edilmesi — şifre sıfırlama linklerinden cache zehirlemesine, iç ağa erişime kadar uzanan bir manipülasyon zinciri.

HTTP Host Header Password Reset Poisoning Routing-based SSRF
01

Mekanizma

HTTP/1.1'de her istekte Host başlığı bulunur ve istemcinin hangi alan adına erişmek istediğini belirtir. Bir sunucu tek IP üzerinden çok sayıda siteyi barındırabildiği için (sanal host) bu başlık gereklidir.

İstek
GET /login HTTP/1.1
Host: ornek.com

Kök neden: Host başlığı istemci tarafından kontrol edilir — yani kullanıcı girdisidir ve güvenilmemelidir. Uygulama bunu doğrulamadan kullanırsa davranışı manipüle edilebilir.

Mutlak URL üretme
şifre sıfırlama linki, e-posta bağlantıları
Yönlendirme adresi
redirect hedefi oluşturma
Statik kaynak yolu
JS/CSS asset URL'leri
Multi-tenant yönlendirme
hangi müşterinin sitesi olduğunu belirleme
Cache anahtarı / log
önbellekleme ve kayıt mantığı

Örneğin PHP'de $_SERVER['HTTP_HOST'], Django'da request.get_host(), Express'te req.headers.host doğrudan kullanıldığında risk doğar.

2

Web Cache Poisoning

Uygulama Host değerini yanıta yansıtıyor (örneğin bir script URL'sinde) ve bu yanıt bir ön bellek (CDN, reverse proxy) tarafından saklanıyorsa, sonraki tüm ziyaretçilere saldırganın içeriği sunulabilir.

İstek → Yansıyan yanıt
GET / HTTP/1.1
Host: saldirgan.com

↓ yanıt
<script src="https://saldirgan.com/static/app.js"></script>

Cache bu yanıtı meşru anahtarla saklarsa durum kalıcı XSS'e dönüşebilir.

3

Rota Tabanlı SSRF

Ön yüzde bir load balancer veya reverse proxy, isteği Host değerine göre arka uca yönlendiriyorsa, saldırgan başlığı iç ağ adresiyle değiştirerek dışarıdan erişilemeyen sistemlere (yönetim panelleri, metadata servisleri) ulaşabilir.

İstek
GET / HTTP/1.1
Host: 192.168.0.1
4

Erişim Kontrolü / Authentication Bypass

Bazı uygulamalar "yönetim paneline yalnızca localhost veya iç alan adından erişilebilir" mantığını Host başlığına bakarak uygular. Başlık sahte olabileceği için bu kontrol kolayca atlatılır.

İstek
GET /admin HTTP/1.1
Host: localhost
5

Sanal Host Brute Force

Aynı sunucuda dışarıya açık olmayan gizli sanal host'lar (intranet.sirket.com, dev.sirket.com gibi) olabilir. Saldırgan Host başlığını bir sözlükle deneyerek bunları keşfeder.

6

Açık Yönlendirme ve Yansıtılmış XSS

Host değeri doğrudan yönlendirme veya HTML çıktısına konursa kullanıcıyı kötü amaçlı bir siteye yönlendirmek ya da script enjekte etmek mümkün olur.

7

Bağlantı Durumu Saldırıları

Bazı sunucular aynı TCP bağlantısındaki ilk isteği doğrular, sonrakilerini doğrulamaz. Saldırgan ilk istekte geçerli, ikinci istekte sahte Host göndererek doğrulamayı atlayabilir.

03

Başlık Manipülasyon Teknikleri

Uygulama doğrudan Host değişikliğini engelliyorsa saldırganlar şu yolları dener.

AAlternatif başlıklar (override)

Arkadaki uygulama bunları Host yerine okuyorsa, ön yüz doğrulama yapsa bile açık kalır.

X-Forwarded-Host: saldirgan.com
X-Host: saldirgan.com
X-Forwarded-Server: saldirgan.com
X-HTTP-Host-Override: saldirgan.com
Forwarded: host=saldirgan.com

BÇift Host başlığı

Ön yüz ilkini, uygulama ikincisini okuyabilir — iki bileşenin farklı değerleri işlemesi açığa yol açar.

Host: ornek.com
Host: saldirgan.com

CPort alanına enjeksiyon

Bazı doğrulamalar yalnızca alan adı kısmına bakar, port alanını kontrol etmez.

Host: ornek.com:saldirgan-payload

DMutlak URL kullanımı

Sunucular istek satırındaki URL ile Host başlığını farklı işleyebilir.

GET https://saldirgan.com/ HTTP/1.1
Host: ornek.com

ESatır sonu / boşluk varyasyonları

Başlıkta girinti (indentation) veya satır katlama ile doğrulayıcı mantığı şaşırtma.

04

Savunma Yöntemleri

1İzin listesi (whitelist) doğrulaması

En önemli savunma. Uygulamanın kabul edeceği alan adlarını sabit olarak tanımlayın, eşleşmeyen istekleri reddedin.

Django
ALLOWED_HOSTS = ['ornek.com', 'www.ornek.com']
Nginx — bilinmeyen Host'ları düşürme
server {
    listen 80 default_server;
    return 444;   /* bağlantıyı kapat */
}

server {
    listen 80;
    server_name ornek.com www.ornek.com;
    # ...
}

Apache: UseCanonicalName On ve doğru ServerName tanımı.

Express (kavramsal)
const izinli = ['ornek.com', 'www.ornek.com'];
app.use((req, res, next) => {
  if (!izinli.includes(req.hostname)) {
    return res.status(400).send('Gecersiz Host');
  }
  next();
});

2Mutlak URL'leri Host'tan üretmeyin

Şifre sıfırlama gibi kritik bağlantılarda alan adını yapılandırma dosyasından alın — bu tek başına parola sıfırlama zehirlemesini tamamen engeller.

Python
BASE_URL = "https://ornek.com"   # config'den
reset_link = f"{BASE_URL}/reset?token={token}"
Override başlıklarını devre dışı bırakınX-Forwarded-Host gibi başlıkları yalnızca güvenilir reverse proxy'den geliyorsa kabul edin; aksi halde yok sayın veya ön yüzde temizleyin.
Reverse proxy / load balancer yapılandırmasıYalnızca bilinen alan adlarını arka uca yönlendirin, iç ağ adreslerini Host olarak kabul etmeyin, cache anahtarına Host'u dahil edin.
Gereksiz iç sistemleri ayırınİç uygulamaları genel IP üzerinde barındırmak yerine ağ seviyesinde ayırın; erişim kontrolünü Host'a değil IP ve kimlik doğrulamaya dayandırın.
Şifre sıfırlama tasarımıToken'ları tek kullanımlık ve kısa ömürlü yapın, sıfırlama sonrası bildirim gönderin, mümkünse ek doğrulama ekleyin.
05

Savunma Amaçlı Test

Kendi uygulamanızı kontrol etmek için (yalnızca yetkiniz olan sistemlerde):

  • 01Host değiştirme testi: curl -i -H "Host: test.example" https://siteniz.com/ — yanıtta test.example yansıyor mu veya farklı davranış var mı bakın.
  • 02Override başlıkları: curl -i -H "X-Forwarded-Host: test.example" https://siteniz.com/
  • 03Şifre sıfırlama e-postasındaki linkin alan adını kontrol edin.
  • 04Burp Suite (Repeater, Intruder) veya OWASP ZAP ile otomatik tarama yapın.
